# AI-Polish — AI 티 제거 규칙

> **사용자 원칙**: "AI가 한 게 누가 봐도 티나" 라는 지적이 가장 치명적이다.
> 클라이언트·공공기관에 제출하는 어떤 산출물도 *AI가 만들었음이 드러나면* 가치가 0이 된다.
> 본 스킬은 그런 흔적을 식별·제거하는 규칙을 누적한다.

## 트리거 신호 (사용자 발화)

다음 표현이 사용자 발화에 등장하면 본 스킬을 즉시 활성화:
- "AI 티 (난다 / 나)"
- "AI스럽다 / GPT 같다 / ChatGPT 같다"
- "사족 / 변명조 / 메타적"
- "고객사에 줄 수 없는"
- "labeling (이상하다 / 고쳐)"
- "polish 해줘"
- "한국 공공기관 문서 같지 않다"

## 지적을 기다리지 않는다

위 신호는 **이미 늦은** 경우다. 지적이 들어왔다는 것은 산출물이 한 번 사용자 앞에 나갔다는 뜻이다.
다음 상황에서는 지적이 없어도 본 스킬을 적용한다.

- 장표·문서·엑셀을 **새로 만드는 중** — 쓰면서 적용한다. 사후 교정으로 미루면 이미 문장 구조가 굳어 있다.
- 클라이언트·공공기관에 나가는 산출물의 문구를 손댈 때
- 케인즈그룹 장표 작업(`keynes-group-design`) 어느 단계에서든

활성화 시 행동:
1. **현재 작업 중인 산출물에서 본 스킬의 모든 규칙을 적용해 재검토**
2. **사용자가 지적한 *새로운* 패턴이 본 스킬에 없으면 → 본 SKILL.md 하단 "추가 패턴" 섹션에 누적**

## 기준 문체

**중앙부처 3급 이상이 결재한 공문서.** 판단이 아니라 조치를 적고, 약어와 실무 은어를 쓰지 않으며,
자기 평가와 자극적 표현을 넣지 않는다. 어떤 문구를 넣을지 망설여지면 이 기준으로 판정한다.

## 규칙 1 — 장식 기호 (Decorative Symbols)

### 금지
- `▣` `■` `◆` `◇` `▶` `★` `☆` `⭐` `✓` `✗` `→` `※` 등 본문 강조용 장식
- `①②③` `ⓐⓑⓒ` 등 원문자 (단, **원본 자료가 이미 그렇게 표기**한 경우는 유지)
- `─────` `═════` 같은 ASCII 구분선
- 절·항 헤더의 이모지 (📁 📊 ⚠️ 🔴 🟠 🟡 🟢)

### 대체
- 한국 공공기관 문서 관행: `Ⅰ. Ⅱ. Ⅲ.` (장) / `1. 2. 3.` (절) / `가. 나. 다.` (항) / `1) 2) 3)` (목)
- 강조: bold (`**`) 또는 단순 `-` bullet
- 구분: 빈 줄 또는 마크다운 `---` 한 번만

### 예
- ❌ `▣ 1. 전체 요약`
- ✓ `1. 전체 요약`

## 규칙 2 — 메타-자기해설 / 방어적 사족

### 금지 표현 (안 물어본 자기변명)
- "본 파일은 ~이 아니라 ~을 목표로 합니다"
- "다만 본 ~은"
- "이번 MVP에서 의도적으로 제외한 것"
- "학술적 완벽함이 아니라"
- "별도 시스템이 아닌 경량형"
- "한계가 있을 수 있으나"
- "참고용으로만 활용"
- "추가 검증이 필요할 수 있습니다"
- "보다 정확한 결과를 위해서는"

### 원칙
**클라이언트는 *결과의 권위*를 사고, *과정의 한계*를 사고 싶지 않다.**
문서 서두에 "본 보고서는 부족합니다"부터 시작하지 말 것.
한계가 진짜 있으면 그 자체를 *별도 섹션*에 명시하되 변명조가 아닌 *조건·전제*로 표현.

### 대체
- 사실 진술 only: "본 파일은 모집단 프레임 관리 도구이다."
- 한계는 별도 절: "Ⅴ. 적용 범위 및 한계"
- 자신감 있는 단언

## 규칙 3 — AI 작업 흔적 노출 표현

### 금지
- "자동 추천 / 자동 산출 / 자동 생성 / 자동 분류"
- "추천 규칙 / 산출 로직 / 산출 규칙"
- "(자동 통과)" 같은 메타 코멘트
- "스크립트로 생성", "build_*.py", "빌드 정보:" 등 도구·코드 흔적
- 산출물 메타데이터에 작성 시각·도구명 노출

### 원칙
**자동 처리든 수동 처리든 *결과만* 보여준다.** 작성 *방법*은 별도 기술문서로.

### 대체
- "자동 추천" → 그냥 "추천" 또는 빼기
- "자동 산출 규칙" → "산정 기준"
- "(자동 통과)" → 삭제

### 예
- ❌ `▣ frame_status 자동 추천`
- ✓ `frame_status 추천 기준`
- ❌ `IF source_method = official → DQS = 1`  (코드 의사문법)
- ✓ `공식자료인 경우 DQS 1을 부여한다.`

### 금지
- "Top 30 / Top 10" → "상위 30건"

### 원칙
**한국 공공기관 문서는 한국어 본문 + 괄호 안 영문/약어** 패턴.

## 규칙 5 — 친절·설명조 (Tutorial Voice)

### 금지
- "~해 주십시오 / ~해 보시기 바랍니다 / ~라고 보면 됩니다"
- "참고로 / 덧붙이자면 / 한편"
- 안 물어본 추가 설명·맥락
- "사실은 ~", "결국 ~", "쉽게 말하면 ~"

### 원칙
**공공기관/컨설팅 문서는 사실 진술형 + 종결어미 `~이다 / ~한다 / ~하였다`.**
"~합니다"체는 클라이언트 대면 발표용에만.

## 규칙 6 — 과도한 양적 표현 / 자기 칭찬

### 금지
- "-37.5% / +88% / -90%" 같은 백분율 자랑
- "최초의 / 사상 최초 / 혁신적인"

### 원칙
**숫자는 표 안에, 자기 평가 없이.** 효과는 *클라이언트가 판단*하게 둔다.

## 추가 패턴 (사용자 지적 누적)

> 사용자가 새로운 "AI 티" 패턴을 지적할 때마다 아래에 추가.
> 형식: `### YYYY-MM-DD — 패턴명` + 사례 + 대체.

### 2026-07-27 — 판단·사고 과정 노출 ("~ 필요")
사례: 장표 본문에 "제도 개선 필요", "추가 분석 필요", "데이터 확보 시급", "효과가 있을 것으로 보임"
이유: 무엇이 부족한지를 적는 것은 **검토 메모**다. 산출물은 결론이어야 한다. 작성자가 생각하는 과정이 그대로 남으면 AI가 훑고 지나간 흔적으로 읽힌다.
대체: 필요를 적지 말고 조치를 적는다 — "데이터 확보 필요" → "○○ 데이터 확보 방안" 또는 확보할 대상·방법을 직접 기술.
금지 어미: `필요` `요망` `시급` `판단됨` `사료됨` `예상됨` `추정됨` `보임` `불가피` (문장 끝)
원칙: **작도 단계에서부터 적용한다.** 사후 polish 로 미루면 이미 장표 구조가 판단 나열로 굳어 있다.

### 2026-07-27 — 자극적 등급·순위 표현
사례: "경평 D 탈출", "경영평가 등급 탈출 방안", "위기 극복 전략"
이유: 발주처의 낮은 평가를 자극적으로 되받는 표현. 제안서에서 발주처를 깎는 인상을 준다. 공문서 문체가 아니다.
대체: "경영실적 평가 대응 체계 정비", "평가지표별 개선과제 도출"
금지: `탈출` `꼴찌` `추락` `폭탄` `초비상` `돌파구` `사활` `생존 전략` `위기 극복`

### 2026-07-27 — 약어·구어
사례: "경평", "공운법"
이유: 공문서는 첫 등장에서 정식 명칭을 쓴다. 약어는 내부 회의체 언어다.
대체: "경영실적 평가", "공공기관의 운영에 관한 법률"

### 2026-07-27 — 실무 은어(판교어)
사례: "핵심 니즈", "전략 정렬 체계", "핵심 인사이트", "액션 아이템", "온보딩 절차"
이유: IT·스타트업 실무 은어. 중앙부처 3급 이상이 결재하는 공문서에는 등장하지 않는다.
대체 대응표:

| 은어 | 표준 용어 |
|---|---|
| 니즈 | 수요, 요구사항 |
| 인사이트 | 시사점 |
| 얼라인 / (전략) 정렬 | 정합성 확보, 연계 |
| 액션 아이템 / 액션플랜 | 추진과제, 세부 실행계획 |
| 온보딩 | 초기 정착 지원 |
| 스코프 | 과업 범위 |
| 리소스 | 자원, 인력·예산 |
| 임팩트 | 파급효과 |
| 페인 포인트 | 애로사항 |
| 캐파 | 처리 역량 |
| 팔로업 | 후속 조치 |
| 오너십 | 책임 소재 |
| 디테일 | 세부사항 |

원칙: **정책 문서에서 이미 굳은 말(로드맵·모니터링·거버넌스)까지 억지로 바꾸지 않는다.** 실무 은어만 걷어낸다.


### 2026-05-26 — "▣ + 자동 추천" 라벨
사례: `▣ frame_status 자동 추천`, `▣ DQS 자동 산출 규칙`
대체: `frame_status 추천 기준`, `DQS 산정 기준`
이유: ▣ 장식 기호 + "자동"이라는 AI 작업 흔적 = 이중으로 AI 티

### 2026-05-26 — "학술적 완벽함이 아니라 ~" 류 선제적 사과
사례: README의 "■ 설계 원칙 — 학술적 완벽함이 아니라 경량 관리체계"
대체: 해당 섹션 통째로 삭제. 사실 진술만.
이유: 클라이언트가 학술적 완벽함을 의뢰한 적도 없는데 미리 변명 = 자신감 결여 신호.

### 2026-05-26 — 나이브한 즉석 조어 (정책 용어 미숙)
사례: "핵심필드 완성", "간편검토", "정보갱신", "중점검토", "기준유지", "신규검토", "모집단 프레임", "DQS"
이유: AI가 머리 굴려서 만든 표현. 통계청·공공기관 정책 문서 표준 용어가 아님. *짜치는* 티 남.

**원칙**: 통계·정책·법령 영역 문서는 **해당 분야 정부기관 표준 용어**를 그대로 차용. 모르면 *추측하지 말고* 웹조사·서브에이전트로 표준 용어 확인 후 사용.

**통계 영역 표준 용어 매핑** (출처: 통계청 「표본설계 및 관리지침」 예규 제183호, 「자체통계품질진단매뉴얼」 2024, 국가데이터처 사업체조사 운영 관행):

| 임시 표현 (AI) | 통계청 표준 |
|---|---|
| 모집단 프레임 | **조사틀** (표본조사면 **표본추출틀**) |
| Data Quality Score / DQS | **자료품질** 또는 통계청 6대 차원(관련성·정확성·시의성·정시성·비교성·일관성) |
| 핵심필드 완성 | **필수항목 기재** |
| 수집방식 / source_method | **자료원** 또는 **수집방법** |
| 기준유지 | **유지** |
| 간편검토 | **확인** |
| 정보갱신 | **갱신** |
| 중점검토 | **정밀검토** |
| 제외검토 | **제외 후보** |
| 신규검토 | **신규 편입** |
| frame_status | **편입 상태** |
| review_type | **정비 유형** |
| review_result | **정비 결과** |
| change_status | **변동사항** |

### 2026-05-29 — 변경량·카운트 노출 (을 입장에서 부담 신호)
사례: 보고서 표지·KPI에 "변경 적용 458건 / 수정·신설·삭제 151·168·10 / 격년 20" 같은 숫자 박스
이유: 발주처가 "히엑? 이렇게 많이 바꾼다고?" 라는 인상부터 받음. 용역사가 변경량을 자랑하는 톤 자체가 을 입장과 안 맞음.

원칙: 발주처에 변경 *결과의 가치*를 보여주되 *변경량 자체*는 부각하지 않음.

### 2026-05-29 — "변경사항" 단정 톤 (용역사 신분 위반)
사례: "조사표 주요 변경사항 분석 리포트", "변경 적용", direction 종결 "~ 신설 / 정렬 / 적용"
이유: 용역 수행사는 을. 발주처에 단정적으로 "이렇게 바꿨다"가 아니라 "이렇게 제안드린다".
대체:
- 제목: "주요 변경사항" → "변경 제안사항"
- KPI: "변경 적용" → "변경 제안"
- direction 종결: "~ 신설" → "~ 신설 제안", "~ 적용" → "~ 적용 제안", "~ 정렬" → "~ 정렬 제안"

원칙: 단언 → 제안 톤. "~을 제안함" 명사형 어휘 통일.

### 2026-05-29 — "관련 매트릭스 안내문 참조" placeholder

이유: 클라이언트는 "그래서 어디?"라고 묻는다. AI가 매핑을 사고 안 한 게으른 흔적.
대체:
- 각 영역에 어떤 gid가 그 시연 단위인지 매번 직접 사고

이유: "보라고 해놓고 줄여놓으면 뭘 보라는 거지?" — 핵심을 잘라 보여주는 것 자체가 무의미.
대체: 첫 마침표·줄바꿈까지만 추출, 자르기 "..." 없음. 셀 안에서 자연 줄바꿈으로 전체 표시.
원칙: 핵심이 안 들어오면 차라리 짧은 표준 표현. 자르기 "..." 흔적은 게으름의 가시화.

### 2026-05-26 — 완성형 종결어미 (~한다 / ~이다)
사례: "조사대상의 포함 기준을 함께 기록한다.", "본 파일은 ... 위한 작업 프레임이다."
이유: 한국 통계·정책 문서의 표·체크리스트·서식·매뉴얼은 **완성형 문장을 거의 쓰지 않음**. 명사 또는 명사형으로 종결.

**종결어미 규칙**:

| 문서 유형 | 종결 패턴 | 예시 |
|---|---|---|
| 행정규칙·법령 본문 | "~한다" / "~로 한다" | "조사대상은 ... 사업체로 한다" |
| 표·체크리스트 셀값 | 명사 단독 | "확정", "제외", "갱신" |
| 매뉴얼·서식 항목 | 명사 또는 "~함" / "~임" | "필수항목 기재 여부", "변동사항 확인" |
| 정의·범위 기술 | "~을 제외함", "~에 한함", "~을 포함" | "농림·어업(개인경영) 등을 제외함" |
| 절차·작업 기술 | 명사형 ("실시", "수행") | "명부 정비 실시", "정합성 검토 수행" |

**금지 패턴**:
- "~한다." (서식·표·매뉴얼에서)
- "~이다."
- "~합니다." (대면 발표용 외)
- "~할 예정입니다."
- "~해 주시기 바랍니다."

**허용 패턴**:
- "유지", "갱신", "확인" (명사 단독)
- "필수항목 기재 여부" (명사형 어구)
- "본 자료는 ... 관리용 조사틀임" ("~임")
- "... 제외함", "... 포함함" (서술이 꼭 필요할 때)
